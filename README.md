# MT5-GOD

`MT5-GOD` — модульная Python-система для автоматизации пайплайна обработки торгового сигнала:

```text
capture -> analyze -> execute
```

Проект построен вокруг трех заменяемых адаптеров: получение входного изображения, анализ изображения и формирование структурированного намерения, затем безопасное исполнение через интерфейс MetaTrader 5.

Главный акцент проекта — архитектура автоматизированного процесса: единые контракты данных, заменяемые модули, проверка результата и безопасный режим `dry_run` по умолчанию.

## Важное ограничение

По умолчанию система запускается в безопасном режиме `dry_run`. Это значит, что пайплайн можно проверять без реального исполнения торгового действия.

Реальный UI-исполнитель MetaTrader 5 включается только через конфигурацию и требует дополнительных зависимостей для работы с экраном, изображениями и распознаванием.

Проект не является инвестиционной рекомендацией и не гарантирует корректность торговых решений. Его смысл — показать архитектуру безопасного автоматизационного конвейера.

## Основная идея

В проекте есть три логических этапа:

1. `Capture` — получить и сохранить входные данные.
2. `Analyze` — извлечь из входных данных структурированное намерение.
3. `Execute` — передать намерение исполнителю.

Эти этапы связаны не напрямую, а через контракты данных. Благодаря этому можно заменить конкретную реализацию одного этапа, не переписывая всю систему.

Например:

- локальный файл можно заменить Telegram-источником;
- простой анализатор можно заменить OCR/vision-анализом;
- dry-run исполнитель можно заменить UI-исполнителем;
- executor можно проверить отдельно на подготовленном JSON.

Статус: **модульный прототип пайплайна автоматизации**.

## Архитектура

Основные компоненты:

```text
app/
  cli.py             # командный интерфейс
  bootstrap.py       # сборка runtime-контекста
  domain/            # доменные модели и режимы
  adapters/          # реализации capture/analyze/execute
  orchestrator       # связывает этапы пайплайна

config/
  *.yaml             # настройки режимов, источников и исполнителей

tests/
  ...                # тесты

examples/
  trade_intent.json  # пример подготовленного намерения сделки
```

Логический поток:

```text
изображение
  -> CaptureAdapter
  -> capture_event
  -> AnalyzerAdapter
  -> analysis_result
  -> trade_intent
  -> ExecutorAdapter
  -> execution_result
```

## Адаптеры

### `CaptureAdapter`

Отвечает за получение входного объекта.

Возможные источники:

- локальный файл;
- Telegram;
- другой внешний источник.

На выходе формируется событие о получении изображения. В этом событии должны быть метаданные, путь к файлу, источник и идентификаторы, которые позволяют избежать повторной обработки одного и того же входа.

### `AnalyzerAdapter`

Отвечает за анализ входного изображения.

Его задача:

- прочитать изображение;
- извлечь важные поля;
- нормализовать данные;
- оценить уверенность;
- провести валидацию;
- сформировать `trade_intent`.

`trade_intent` — центральная структура, которая передается на этап исполнения. Исполнитель не должен догадываться, как были получены данные; он должен работать с уже нормализованным объектом.

### `ExecutorAdapter`

Отвечает за исполнение подготовленного намерения.

Поддерживается безопасная логика:

- `dry_run` для проверки без реального действия;
- отдельная команда исполнения подготовленного JSON;
- тестовый проход по аккаунтам;
- возвращение структурированного результата.

Если включается UI-исполнитель для MT5, он должен работать через интерфейс приложения, а не через торговый Python API.

## Контракт данных

Основная идея проекта — единый контракт между этапами.

Упрощенно:

```text
capture_event
  -> analysis_result
  -> trade_intent
  -> execution_result
```

Такой контракт позволяет:

- тестировать этапы отдельно;
- сохранять промежуточные результаты;
- повторять выполнение с того же состояния;
- заменять адаптеры;
- отлаживать пайплайн без реального исполнения.

## Установка

Требуется Python `3.11+`.

```powershell
python -m venv .venv
.venv\Scripts\Activate.ps1
pip install -e .[dev]
```

Дополнительные зависимости ставятся по необходимости.

Telegram-адаптер:

```powershell
pip install -e .[telegram]
```

Vision/OCR-зависимости:

```powershell
pip install -e .[vision]
```

UI-исполнитель:

```powershell
pip install -e .[ui]
```

## Команды

Запуск Telegram ingestion:

```powershell
python -m app run-bot
python .\run_bot.py
.\run_bot.bat
```

Анализ одного изображения без исполнения:

```powershell
python -m app analyze .\path\to\image.png
```

Полный одноразовый прогон через pipeline:

```powershell
python -m app run-once .\path\to\image.png
```

Исполнение подготовленного `trade_intent`:

```powershell
python -m app execute .\examples\trade_intent.json
```

Проверка аккаунтов:

```powershell
python -m app test-accounts
```

## Режимы работы

Проект рассчитан на несколько режимов:

- `dry_run` — полный прогон без реального исполнения;
- `analyze_only` — только анализ изображения;
- `execute_only` — исполнение заранее подготовленного JSON;
- `full_pipeline` — полный цикл от входного изображения до исполнения.

Такая декомпозиция нужна, чтобы проверять систему по частям. Например, можно сначала проверить анализ, затем отдельно проверить исполнителя на уже готовом `trade_intent`.

## Конфигурация

Основные настройки выносятся в YAML-файлы и `.env`.

В конфигурацию должны уходить:

- режим запуска;
- пути к данным;
- настройки Telegram;
- профили анализа;
- настройки OCR;
- настройки UI;
- список аккаунтов;
- политики повторных попыток;
- флаг `dry_run`;
- пороги уверенности.

Секреты не должны храниться в коде. Для них используется `.env` или переменные окружения.

## UI-исполнение в MetaTrader 5

Одна из особенностей проекта — идея исполнения через визуальный интерфейс MT5.

Это означает:

- запуск терминала как desktop-приложения;
- поиск элементов интерфейса;
- ввод параметров через клавиатуру и мышь;
- проверка экранного состояния;
- сохранение скриншотов успеха или ошибки.

Такой подход сложнее прямого API, но он демонстрирует задачу UI-автоматизации: проект должен уметь работать с внешней программой как пользователь, а не только через библиотечный интерфейс.

## Проверка и тесты

```powershell
pytest
```

Тесты важны для такого проекта, потому что пайплайн состоит из нескольких этапов, и ошибка на одном этапе не должна незаметно переходить в следующий.

Особенно важно проверять:

- корректность моделей данных;
- валидацию `trade_intent`;
- работу `dry_run`;
- поведение оркестратора;
- обработку ошибок;
- идемпотентность повторной обработки.
