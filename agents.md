# Техническое задание

## Проект: модульная система автоматизации торгового ввода через компьютерное зрение

## 1. Цель проекта

Разработать на Python модульную систему из трех независимых, взаимозаменяемых модулей, которая реализует непрерывный конвейер:

**сохранение данных → анализ и подготовка данных → ввод данных**

Этот конвейер должен сохраняться независимо от того, какая реализация стоит за каждым модулем.

Система должна:

1. принимать изображения из заданной Telegram-группы и конкретной ветки внутри нее;
2. сохранять изображения и метаданные;
3. анализировать изображение калькулятора и извлекать параметры сделки;
4. подготавливать нормализованные данные сделки;
5. запускать MetaTrader 5 как обычное desktop-приложение;
6. выполнять ввод параметров сделки **только через визуальный интерфейс**, без использования торговых API MT5 для Python;
7. при необходимости переключаться между аккаунтами и повторять сценарий открытия сделки.

---

## 2. Ключевое архитектурное требование

Система должна быть **строго модульной**.

Каждый модуль должен быть заменяемым без переписывания остальной системы, если новая реализация соблюдает единый контракт входных и выходных данных.

### Инвариант системы

Независимо от реализации модулей, всегда должен сохраняться один и тот же логический поток:

1. **Capture stage** — получение и сохранение исходных данных;
2. **Analyze stage** — анализ изображения и построение нормализованной структуры сделки;
3. **Execute stage** — ввод параметров сделки через визуальный интерфейс.

---

## 3. Общие ограничения

### 3.1. Технологические ограничения

1. Язык разработки: **Python 3.11+**.
2. Целевая ОС: **Windows 10/11**.
3. Запуск MetaTrader 5 должен выполняться через `os.startfile(...)`.
4. Торговые действия в MT5 запрещено выполнять через:

   * официальный Python-модуль MT5,
   * любые прямые вызовы торговых функций терминала,
   * DLL/IPC-обходы, которые фактически заменяют UI-ввод.
5. Взаимодействие с MT5 должно происходить **только через экранный UI**:

   * поиск элементов интерфейса визуально;
   * OCR/распознавание;
   * клики, двойные клики, ввод с клавиатуры;
   * ожидание появления/изменения экранных состояний.

### 3.2. Функциональные ограничения

1. Система не должна открывать сделку, если данные не прошли валидацию.
2. Система не должна открывать сделку повторно по одной и той же картинке, если уже есть успешный результат обработки.
3. Любая ошибка должна фиксироваться в логах и в статусе задачи.
4. Каждый этап должен быть повторяемым и идемпотентным настолько, насколько это возможно.

### 3.3. Организационные ограничения

1. Все секреты должны храниться вне кода: через `.env` или системные переменные окружения.
2. Все пути, шаблоны UI, настройки OCR, Telegram-идентификаторы, список аккаунтов, профили исполнения — только в конфигурации.
3. Система должна поддерживать режимы:

   * `dry_run` — полный прогон без отправки ордера;
   * `analyze_only` — только анализ;
   * `execute_only` — только ввод уже готового `trade_intent`;
   * `full_pipeline` — полный цикл.

## 4. Общая архитектура

Система должна состоять из следующих логических компонентов:

### 4.1. Оркестратор

Отдельный слой, который не зависит от конкретной реализации модулей и управляет пайплайном:

* принимает событие о новом изображении;
* вызывает модуль анализа;
* получает нормализованный `trade_intent`;
* вызывает модуль исполнения;
* обновляет статусы обработки;
* сохраняет результаты.

### 4.2. Модуль 1 — UI-исполнитель для MT5

Отвечает за:

* запуск MT5;
* визуальный поиск нужной валютной пары;
* открытие формы ордера;
* заполнение полей;
* отправку ордера;
* переключение аккаунта;
* повтор сценария для другого аккаунта.

### 4.3. Модуль 2 — модуль анализа изображения

Отвечает за:

* обработку скриншота калькулятора;
* OCR/распознавание необходимых значений;
* нормализацию данных;
* валидацию;
* формирование единого объекта `trade_intent`.

### 4.4. Модуль 3 — Telegram ingestion

Отвечает за:

* отслеживание сообщений в заданной группе и заданной ветке;
* сохранение изображений;
* создание задания на анализ;
* передачу управления оркестратору.

### 4.5. Слой хранения

Должен сохранять:

* оригинальные изображения;
* промежуточные результаты анализа;
* итоговые нормализованные данные сделки;
* статусы задач;
* скриншоты ошибок;
* журнал действий;
* результаты исполнения.

## 5. Требование к взаимозаменяемости модулей

Каждый модуль должен быть оформлен как **адаптер**, реализующий общий интерфейс.

Поддержать два уровня интеграции:

1. **Python interface** — для прямого вызова внутри проекта;
2. **CLI interface** — чтобы модуль можно было заменить внешним процессом.

### 5.1. Базовые интерфейсы

#### CaptureAdapter

Принимает внешний источник и возвращает событие о новом входном объекте.

#### AnalyzerAdapter

Принимает сохраненный объект изображения и возвращает:

* структурированные поля;
* нормализованный `trade_intent`;
* confidence score;
* сообщения валидации.

#### ExecutorAdapter

Принимает `trade_intent` и возвращает:

* статус исполнения;
* результаты по каждому аккаунту;
* скриншоты подтверждения/ошибки;
* технический лог шагов.

# 9. МОДУЛЬ 1 — UI-автоматизация MetaTrader 5

## 9.1. Назначение

Модуль должен управлять MT5 **только визуально** и выполнять открытие сделки на одном или нескольких аккаунтах.

## 9.2. Сценарии

### Сценарий A — открытие сделки на текущем аккаунте

1. Запустить MT5 через `os.startfile(path_to_terminal)`.
2. Дождаться появления главного окна.
3. Найти в левой панели “Символы” нужную валютную пару.
4. Дважды нажать по валютной паре.
5. Дождаться открытия панели нового ордера.
6. Ввести необходимые значения:

   * направление сделки, если это требует UI;
   * объем;
   * Stop Loss;
   * Take Profit;
   * при необходимости цену;
   * комментарий, если поле доступно.
7. Нажать кнопку отправки ордера.
8. Дождаться визуального подтверждения успешной отправки или сообщения об ошибке.
9. Сохранить результат.

### Сценарий B — переключение аккаунта и повтор сделки

1. Нажать вкладку `Файл`.
2. Переключиться на нужный аккаунт из списка или через доступный UI-сценарий переключения.
3. Дождаться полной загрузки аккаунта и готовности интерфейса.
4. Повторить сценарий A.
5. Выполнить цикл для всех аккаунтов, указанных в `trade_intent.accounts`.

---

## 9.3. Обязательные требования к модулю 1

### 9.3.1. Визуальное управление

Нельзя использовать Python API MT5 для:

* отправки ордеров;
* получения торговых параметров;
* переключения аккаунтов;
* чтения торгового состояния вместо экранной проверки.

Допустимо использовать системные средства только для:

* запуска приложения;
* активации окна;
* снятия скриншотов;
* управления мышью и клавиатурой.

### 9.3.2. Устойчивость к UI

Модуль должен быть построен не на “жестко зашитых координатах”, а на комбинации:

* шаблонного поиска элементов интерфейса;
* OCR для текстовых областей;
* привязки координат к найденным якорным элементам.

Жесткие координаты допустимы только как резервная стратегия и только через конфиг профиля конкретного терминала.

### 9.3.3. Поддержка профилей UI

Должна быть система UI-профилей, например:

```yaml
ui_profiles:
  default_mt5:
    language: ru
    templates_dir: assets/templates/mt5
    confidence_threshold: 0.88
    anchors:
      symbols_panel: ...
      file_menu: ...
      order_window: ...
      submit_button: ...
```

Это нужно, чтобы заменить шаблоны под:

* другую тему MT5;
* другой язык интерфейса;
* другое разрешение;
* другой DPI.

### 9.3.4. Пошаговая верификация

После каждого действия модуль обязан проверять, что шаг реально выполнен:

* окно MT5 открыто;
* символ найден;
* панель ордера открылась;
* нужное поле стало активным;
* значение реально введено;
* кнопка отправки нажата;
* появился экранный признак успеха либо ошибки.

### 9.3.5. Безопасность отправки

Перед нажатием кнопки отправки ордера модуль обязан:

1. сделать скриншот формы;
2. сравнить введенные значения с `trade_intent`;
3. убедиться, что все обязательные поля заполнены;
4. только после этого отправлять ордер.

# 10. МОДУЛЬ 2 — анализ изображения калькулятора

## 10.1. Назначение

Получить из скриншота значения, необходимые для сделки, нормализовать их и подготовить `trade_intent`.

## 10.2. Вход

На вход модуль получает путь к изображению и метаданные события.

## 10.3. Выход

На выход модуль обязан вернуть:

* извлеченные сырые поля;
* нормализованные поля;
* оценку уверенности;
* список ошибок и предупреждений;
* `trade_intent` либо причину, почему он не построен.

---

## 10.4. Этапы обработки

### Этап 1. Предобработка

1. загрузка изображения;
2. приведение к рабочему формату;
3. коррекция масштаба;
4. выделение ROI;
5. бинаризация/повышение контраста;
6. шумоподавление.

### Этап 2. Детекция зон

Найти на изображении области, содержащие:

* символ;
* направление;
* lot/volume;
* stop loss;
* take profit;
* entry price, если есть;
* риск, если есть.

### Этап 3. OCR/парсинг

Для каждой найденной зоны:

* извлечь текст;
* нормализовать разделители;
* убрать мусорные символы;
* привести числа к типам `float`/`int`;
* привести направление к enum `buy|sell`;
* привести символ к canonical form, например `EURUSD`.

### Этап 4. Пост-обработка

1. проверить обязательные поля;
2. устранить типичные OCR-ошибки;
3. применить правила нормализации;
4. сформировать единый `trade_intent`.

---

## 10.5. Правила валидации

Минимум должны проверяться:

1. `symbol` не пустой;
2. `direction` — только `buy` или `sell`;
3. `volume > 0`;
4. `stop_loss > 0`, если он обязателен;
5. `take_profit > 0`, если он обязателен;
6. если `entry_price` указан, он должен быть числом;
7. confidence по критичным полям не ниже порога;
8. если изображение неразборчиво, задача должна завершаться статусом `failed` или `partial`, но не должна запускать исполнение.

---

## 10.6. Конфигурируемость

Модуль 2 должен поддерживать несколько профилей распознавания под разные типы калькуляторов.

Пример:

```yaml
analysis_profiles:
  calculator_a:
    roi_templates: ...
    ocr_engine: "tesseract"
    required_fields:
      - symbol
      - direction
      - lot
      - stop_loss
      - take_profit
    confidence_thresholds:
      overall: 0.85
      symbol: 0.90
      direction: 0.95
```

---

## 10.7. Хранение результатов анализа

Нужно сохранять:

* исходное изображение;
* размеченную копию с выделенными ROI;
* сырые результаты OCR;
* итоговый JSON результата анализа.

# 11. МОДУЛЬ 3 — Telegram bot / ingestion

## 11.1. Назначение

Получать изображения только из заданного источника Telegram и запускать пайплайн.

## 11.2. Функциональные требования

Модуль должен:

1. отслеживать сообщения в указанной группе;
2. фильтровать сообщения по конкретной ветке/топику;
3. принимать только изображения;
4. сохранять изображения на диск;
5. сохранять метаданные сообщения;
6. вычислять hash изображения для дедупликации;
7. создавать `capture_event`;
8. вызывать оркестратор.

---

## 11.3. Конфигурация источника

Пример:

```yaml
telegram:
  enabled: true
  allowed_chat_id: -1001234567890
  allowed_thread_id: 777
  download_dir: data/inbox
  allowed_mime_types:
    - image/jpeg
    - image/png
    - image/webp
```

---

## 11.4. Правила фильтрации

Сообщение должно быть проигнорировано, если:

* оно пришло не из нужной группы;
* оно пришло не из нужной ветки;
* в нем нет изображения;
* это дубликат по `message_id` или `sha256`, если политика запрещает повторную обработку.

---

## 11.5. Поведение при поступлении изображения

1. скачать файл;
2. сохранить его;
3. создать `capture_event`;
4. сохранить задачу в хранилище;
5. передать в оркестратор;
6. при необходимости отправить технический ответ в Telegram, например:

   * “получено”,
   * “анализ успешен”,
   * “ошибка распознавания”,
   * “отправлено на исполнение”,
   * “сделка выполнена / ошибка исполнения”.

Отправка ответов в Telegram должна быть отключаемой настройкой.

# 12. Оркестратор

## 12.1. Назначение

Оркестратор — это обязательный центральный слой, который связывает все модули и гарантирует неизменность конвейера.

## 12.2. Его обязанности

1. принять `capture_event`;
2. перевести задачу в состояние `QUEUED_FOR_ANALYSIS`;
3. вызвать `AnalyzerAdapter`;
4. сохранить `analysis_result`;
5. если `validation.is_valid = true`, сформировать переход в `READY_FOR_EXECUTION`;
6. вызвать `ExecutorAdapter`;
7. сохранить `execution_result`;
8. обновить конечный статус.

## 12.3. Ключевое требование

Оркестратор не должен знать внутреннюю реализацию модулей. Он должен зависеть только от интерфейсов и контрактов данных.

# 16. Отказоустойчивость

## 16.1. Retry policy

Нужно разделять:

1. retry на уровне Telegram download;
2. retry на уровне OCR;
3. retry на уровне визуального поиска элементов UI;
4. retry на уровне исполнения по аккаунту.

## 16.2. Правила остановки

Сделка не должна отправляться, если:

* анализ невалиден;
* confidence ниже порога;
* окно ордера не подтверждено;
* введенные значения не совпали с `trade_intent`;
* невозможно подтвердить, что выбран нужный аккаунт.

## 16.3. Partial success

Если сделка успешно отправлена на одном аккаунте и не отправлена на другом, общий статус должен быть `partial`, а не `success`.

# 19. Критерии приемки

Система считается выполненной, если соблюдены все условия ниже.

## 19.1. По модулю 3

1. Бот принимает изображение только из заданной группы и заданной ветки.
2. Изображение сохраняется на диск.
3. Формируется `capture_event`.
4. Дубликаты корректно распознаются.

## 19.2. По модулю 2

1. Модуль извлекает ключевые поля из тестовых изображений.
2. Формирует `analysis_result`.
3. Создает валидный `trade_intent` при корректных данных.
4. Не запускает исполнение при невалидном анализе.

## 19.3. По модулю 1

1. MT5 запускается через `os.startfile`.
2. Нужный символ находится визуально.
3. Окно ордера открывается двойным кликом по символу.
4. Поля заполняются в UI.
5. Ордер отправляется только после верификации.
6. Переключение аккаунтов через меню `Файл` работает хотя бы для конфигурируемого списка аккаунтов.
7. На каждом шаге сохраняются скриншоты или логи подтверждения.

## 19.4. По всей системе

1. Полный конвейер работает end-to-end.
2. Любой модуль можно заменить без переписывания остальных, если новый модуль соблюдает контракт.
3. Все этапы логируются.
4. При сбое остается диагностический след.
5. Есть `dry_run`.

# 23. Формулировка, которую можно дать Codex как задачу

Разработай на Python 3.11+ модульную систему автоматизации торгового ввода через компьютерное зрение. В системе три взаимозаменяемых модуля:

1. Telegram ingestion, который сохраняет изображения из конкретной Telegram-группы и конкретной ветки;
2. Analyzer, который обрабатывает скриншот калькулятора, извлекает параметры сделки и формирует нормализованный `trade_intent`;
3. Executor, который запускает MetaTrader 5 через `os.startfile` и выполняет открытие сделки только через визуальный интерфейс, без использования Python API MT5 для торговых действий.

Обязательное требование: независимо от реализации модулей должен сохраняться единый конвейер `сохранение данных -> анализ и подготовка данных -> ввод данных`.
Все модули должны быть заменяемыми через единые интерфейсы и единые JSON/Pydantic-контракты.
Нужны: оркестратор, state machine, файловое/SQLite-хранилище, конфиги, логи, dry-run, тесты, README, `.env.example`, CLI-команды и диагностические артефакты.
Модуль MT5 должен работать через визуальный поиск UI-элементов, OCR, клики и ввод с клавиатуры, с пошаговой верификацией каждого действия и поддержкой переключения аккаунтов через меню `Файл`.
